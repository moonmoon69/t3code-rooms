## What commands exist to create or attach a thread, submit a user turn, interrupt, and answer a pending provider question or permission?

### Takeaway

Shipped client commands cover create, turn submit, interrupt, approval, and user-input. There is no attach command: an existing thread is addressed by its id from the shell snapshot. Turn-start bootstrap that creates the thread is implemented on the WebSocket dispatch path, not on the HTTP dispatch path.

### Inferences

- “Attach” for Phase 1 is subscribe-or-snapshot an existing `threadId` from `GET /api/orchestration/shell` or `orchestration.subscribeShell`. No extra attach RPC is required.
- A no-fork companion that speaks HTTP must `thread.create` (or target an existing id) and then `thread.turn.start`. Putting `bootstrap.createThread` only on an HTTP dispatch does not run the WebSocket pre-step, and the decider rejects a turn start for a missing thread.
- Permission and plan/default mode for an existing thread are `thread.runtime-mode.set` and `thread.interaction-mode.set`. Setting those fields only on `thread.turn.start` does not change what `thread.turn-start-requested` persists.
- The user-doc names line up in order with the four `RuntimeMode` literals, but that string mapping is not written in the user doc.

### Gaps

- Whether HTTP and WebSocket dispatch share one code path in some other layer that still applies bootstrap was not found; the HTTP handler shown calls the engine directly.
- No live check that a given installed T3 build’s dispatch schema matches this commit.

## What persisted events or subscription payloads identify a specific turn’s successful terminal state, failure, interruption, and needs-input, as distinct from thread.settled / auto-settle?

### Takeaway

Turn outcome is session status leaving `running`, projected onto `latestTurn.state`. `thread.settled` is a separate inbox lifecycle event emitted for both manual settle and automatic settlement, and it does not name the turn. Needs-input is pending approval or user-input activity, including while the session is still `running`. The test receipt bus does not publish in production.

The projector settles the turn from session status. A late checkpoint must not extend recorded turn duration. Production runtime receipts are a no-op; tests must use persisted state and events. Durable command receipts are a different mechanism. — [overview.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/overview.md#L53-L92)

### Inferences

- A companion can treat provider completion as: our `thread.turn-start-requested` (`commandId` + `messageId`) is still the pending start when the next `thread.session-set` enters `running` with `activeTurnId`, and that same `turnId` later leaves `running`. Success is `latestTurn.state === "completed"` with session `ready` or `idle`, and shell `hasPendingApprovals` / `hasPendingUserInput` false. Failure is `latestTurn.state === "error"` or activity `provider.turn.start.failed` for our `messageId`. Interruption is session `interrupted` or `stopped` settling that `turnId` to `interrupted`, which is what `turn.aborted` produces.
- Do not treat `thread.settled` as that signal. The event is shared by manual settle and auto-settle. An observer can notice auto-settle only because the event `commandId` uses the `server:auto-settle:` prefix minted in the reactor. That prefix is server source, not a schema literal.
- A provider `turn.completed` with state `interrupted` or `cancelled` is stored as a successful `ready` / `completed` turn under the current ingestion switch. Phase 1 should not assume those provider states survive as `latestTurn.state === "interrupted"`.
- `thread.turn-diff-completed` is the checkpoint milestone. It can be absent, late, or `missing`, and it is not the provider-completion bit. `backgroundLiveness` can be set after the turn has already settled.
- Needs-input can be true while `latestTurn.state` is still `running`, because provider `waiting` stays `running`.
- If another `thread.turn-start-requested` arrives before ours is adopted, the single pending row now points at the other message. Correlating only by “next running turn on this thread” would attribute the wrong turn. The public snapshot does not expose `pendingMessageId`, so the companion has to keep that association from the event stream itself.

### Gaps

- Whether each shipped provider (Claude, Codex, Cursor, OpenCode, Antigravity, Grok) actually emits `turn.completed` versus `turn.aborted` versus `session.state.changed: waiting` for the same user-visible outcome was not traced per adapter.
- No public event field joins client `commandId` to provider `turnId`. The join exists only in the internal turn row.
- Historical turn state for any turn that is no longer `latestTurn` is not on `OrchestrationThread`. A client that connects after the fact sees the latest turn, messages, and checkpoints, not a turn-state log.

## Is there a stable client command ID for idempotent retry?

### Takeaway

Yes. The client supplies `commandId`. The engine persists one receipt per id and replays an accepted receipt without running the command again. The receipt check does not compare the new body to the original body.

### Cited Findings

- `CommandId` is a branded non-empty trimmed string. No UUID pattern is required. Every client command in the union includes `commandId`. — [baseSchemas.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/baseSchemas.ts#L126-L140); [orchestration.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/orchestration.ts#L1079-L1308)
- If a receipt exists for that id and the same aggregate, status `accepted` returns the stored `{ sequence }`. Status `rejected` fails with the stored error. The same id aimed at a different aggregate fails as a command-id conflict. Comment: a receipt proves that exact command was handled, and replaying it for another aggregate would report success for work that never happened. — [OrchestrationEngine.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L144-L171)
- Events, projections, and the accepted command receipt commit in one transaction. Retries are idempotent because of that receipt. Acknowledgement is not provider completion. — [overview.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/overview.md#L53-L66)
- A test named “replays the accepted receipt for a genuine retry of the same command” exists in `OrchestrationEngine.test.ts`. — [OrchestrationEngine.test.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/orchestration/Layers/OrchestrationEngine.test.ts#L1930)
- Receipts are not a client-facing read API in `OrchestrationRpcSchemas`. The client sees `DispatchResult.sequence` or an error. — [orchestration.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/orchestration.ts#L2339-L2372)

### Inferences

- Retry of an uncertain dispatch must resend the same `commandId` and the same aggregate. A changed briefing under the same id is not applied; the old acceptance is returned. A rejected id cannot be reused; a revised instruction needs a new id. That matches the PRD rule that a retry must not rebuild the briefing while reusing the id.
- After reconnect, reconciliation is “did this `commandId` get a receipt?” only indirectly: the companion must look for `thread.message-sent` / `thread.turn-start-requested` with that `commandId`, or treat a replayed `sequence` as acceptance. There is no shipped “get receipt by command id” RPC in the schemas above.

### Gaps

- The engine snippet does not show a payload-equality check. It was not proven whether some earlier normalizer rejects a mismatched body before the receipt lookup.
- Receipt retention lifetime (forever versus compaction of `orchestration_command_receipts`) was not read.

## How does direct activity in the T3 UI interact with an external client submitting to the same thread?

### Takeaway

The UI and a companion are two clients of one server. Commands are serialized and then broadcast. A second turn start while a provider turn is running is sent immediately, except during compaction, when it is queued. There is no lock that reserves a thread for one client.

### Cited Findings

- The event log is the source of truth. The engine serializes commands. Subscribers receive events after the commit. Web, desktop, and mobile clients use the same authenticated RPC boundary. — [overview.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/overview.md#L8-L19) and [L53-L60](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/overview.md#L53-L60)
- `thread.turn.start` from any client emits `thread.turn-start-requested` and, if the thread was settled or snoozed, `thread.unsettled` / `thread.unsnoozed` with `reason: "activity"`. — [decider.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/orchestration/decider.ts#L1459-L1501)
- The provider reactor calls `sendTurn` for a normal turn start even when a session is already running. The only queue is `turnsAfterCompaction`, used while a `/compact` is in progress. A compact is refused while status is `starting` or `running`. — [ProviderCommandReactor.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1416-L1515)
- Ingestion accepts a conflicting `turn.started` when the server has a pending turn start and the provider’s active turn id matches. Comment: steering a running turn makes some providers (for example OpenCode) open a new turn without completing the superseded one. A stale `turn.started` for some other id is rejected when the strict lifecycle guard is on. — [ProviderRuntimeIngestion.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L1793-L1820)
- Client-dispatched events can carry `metadata.origin` `{ surface?, appVersion? }`. `surface` is `web | desktop | mobile | cli`, taken from the `/ws` query `clientSurface`. Absent or malformed values are dropped. The comment says several client types can connect at once, and origin must not become a server-global current client. HTTP dispatch was not shown stamping that origin. — [orchestration.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/orchestration.ts#L1980-L2006); [baseSchemas.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/baseSchemas.ts#L152-L159); [ws.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/ws.ts#L431-L448) and [L522-L532](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/ws.ts#L522-L532)
- Shell updates are coalesced in a 50ms / 512-event window before subscribers see them. — [ws.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/ws.ts#L1007-L1011)

### Inferences

- Direct UI activity on the same thread is visible to the companion as ordinary events whose `commandId` is not the companion’s. It can unsettle the thread, start another turn, answer a pending request, or interrupt. It does not by itself complete the companion’s command id.
- A UI send during a companion turn is a steer, not a queued room task. The previous running turn can be marked `completed` when the new turn starts, which is a false success if a companion treats “previous turn left `running`” without checking that the terminal state belongs to its `turnId`.
- `metadata.origin.surface` can distinguish a desktop/web UI command from a companion that connects with `clientSurface=cli`, but only for WebSocket-dispatched commands that sent the query param. It is not an authorization boundary.

### Gaps

- Exact UI behavior when the user types during an in-flight turn (whether the desktop app sends `thread.turn.start` immediately) was not read in the client package. The server will accept that command if the client sends it.
- HTTP-originated commands may lack `metadata.origin`. A companion using only HTTP is harder to tell apart from the UI by surface.

## What authentication modes exist for a local companion (desktop-managed vs serve vs connect), and which can a no-fork companion use today?

### Takeaway

A no-fork companion can use a one-time pairing token, then a bearer or DPoP session, against `t3 serve` on loopback or against any environment whose policy is `remote-reachable`. It cannot use the desktop app’s private bootstrap token. T3 Connect is an extra hop that still ends in an environment session.

### Cited Findings

- Server process mode is `web | desktop`, not a `serve` enum. `t3 serve` is “Run the T3 Code server without opening a browser and print headless pairing details,” and it sets `startupPresentation: "headless"`. Default mode when no flag, env, or desktop bootstrap says otherwise is `web`. Desktop mode defaults host to `127.0.0.1`. Web mode leaves host unset unless `--host` / `T3CODE_HOST` is set. — [config.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/config.ts#L24-L25); [cli/server.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/cli/server.ts#L26-L35); [cli/config.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/cli/config.ts#L279-L286) and [L379-L386](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/cli/config.ts#L379-L386)
- `EnvironmentAuthPolicy` maps that to `ServerAuthPolicy`: desktop + loopback host → `desktop-managed-local`; desktop + remote host → `remote-reachable`; non-desktop + remote host → `remote-reachable`; non-desktop + loopback or empty host → `loopback-browser`. Empty host is not remote-reachable. Bootstrap methods: `desktop-managed-local` → `["desktop-bootstrap"]`; desktop and `remote-reachable` → `["desktop-bootstrap", "one-time-token"]`; otherwise → `["one-time-token"]`. Session methods are always `browser-session-cookie`, `bearer-access-token`, `dpop-access-token`. — [EnvironmentAuthPolicy.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/auth/EnvironmentAuthPolicy.ts#L18-L42); [utils.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/auth/utils.ts#L66-L79); [auth.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/auth.ts#L11-L78)
- `desktop-bootstrap` is a trusted local desktop handoff so the shell can pair the renderer without a login screen. The grant is delivered on a trusted IPC channel (fd3 or stdin) at backend launch, is reusable, and lives 24 hours. User pairing links use a 12-character token and a 5-minute default TTL. - `unsafe-no-auth` is a schema literal described as an explicit unsafe escape hatch. `EnvironmentAuthPolicy.make` never assigns it. A repo code search on 2026-09-23 found the literal only in `packages/contracts/src/auth.ts`. — [auth.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/auth.ts#L31-L39)
- Docs: desktop local access is **Settings → Connections**, **Network access**, then a pairing link. CLI is `t3 serve --host <private-ip>`, or `t3 pair` against an already running server. Tailscale is `t3 serve --tailscale-serve`. Pairing authorizes that device; links are one-time; the original token is not needed to reconnect. - Ordinary pairing does not grant access-management or relay-management. Standard scopes include `orchestration:read` and `orchestration:operate`. Creating another pairing link requires `access:write` and every delegated scope. A test shows a non-owner paired client receives 401 from `POST /api/auth/pairing-token`. — [environment-auth.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/environment-auth.md#L7-L14); [auth.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/packages/contracts/src/auth.ts#L103-L115); [server.test.ts](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/apps/server/src/server.test.ts#L4890-L4905)
- `T3CODE_DEV_AUTH_TOKEN` is accepted only by web development environments. Desktop and non-development servers ignore it. — [environment-auth.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/environment-auth.md#L40-L46)
- T3 Connect: the relay asks the environment to mint a one-time bootstrap credential bound to the client DPoP key. The client exchanges it with the environment. A relay token is not an environment login. `t3 connect` can offer the background service; declining it means `t3 serve`. Sign-in alone does not publish the machine. — [t3-connect.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/internals/t3-connect.md#L1-L18); [remote-access.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/user/remote-access.md#L6-L21)
- Background service: `t3 service install` on Linux (systemd user, linger) and macOS (login item; stops at logout). Windows services are not supported. `t3 serve` is the documented fallback when linger is unavailable. The service and Connect are managed separately. — [background-service.md](https://github.com/pingdotgg/t3code/blob/34096519121033ccf72cd43ea5350f9482df188a/docs/user/background-service.md)

### Inferences

- Today, without a fork, the companion should pair to a server that advertises `one-time-token`: default `t3 serve` (policy `loopback-browser`), `t3 serve --host <reachable>`, or a desktop app with Network access (policy `remote-reachable`). After pairing, call the HTTP API with the bearer token and open `/ws` with a websocket ticket.
- The desktop app’s everyday local server (`desktop-managed-local`) does not advertise `one-time-token`. A third process cannot complete `desktop-bootstrap` unless it possesses the IPC secret. That secret is not documented as a companion API.
- Connect is usable without a fork, but it is cloud sign-in plus DPoP, not a simpler local socket. A same-machine companion does not need it.
- A paired session with standard scopes can dispatch turns. There is no shipped read-only companion profile in `AuthStandardClientScopes`. “Connect without mutating” is a client choice, not a mode the server offers to ordinary pairing.

### Gaps

- The systemd/launchd argv for `t3 service install` was not read, so it is not confirmed here that the service process is `mode=web` rather than `mode=desktop`.
- How the desktop UI mints a pairing link after Network access is enabled was not traced in the Electron package. The policy table says the server will accept `one-time-token` once the host is remote-reachable.
- Cookie name and exact token-exchange request body were not copied into this note. They live in `packages/contracts/src/auth.ts` and `apps/server/src/auth/http.ts`.

### Inferences

- Spike 1 is answered as a procedure (pair, then read `server.getConfig` and the shell) and unanswered as a dry run against the user’s installed version. Any session that includes `orchestration:operate` can mutate if the client dispatches.
- Spike 2 is answered for message text and checkpoint metadata on this commit, and unanswered for tool-output losslessness and for diff size under a real workspace.
- Spike 3 remains empirical. Source says how a normalized terminal state is recorded. It does not show two harnesses producing that state for a known prompt.
- Spike 4 is answered negatively for a native persona field. A persona brief would be text inside the user message or a thread title. Whether a `RuntimeMode` is actually enforced is provider-specific and still needs a live check; the user doc already says Full access is not universal.
- Spike 5 is partly answered: the server will accept a UI turn on a companion thread, will queue turns across compaction, and will keep command receipts across process restart. What that does to room delivery cursors is a Rooms concern. “Thread rebinding” has a meta-update command; whether the provider session keeps the old cwd after `worktreePath` changes was not traced.
