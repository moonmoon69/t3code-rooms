## Do current docs still describe Choice, Noul, independent questions in one call, confidence semantics, and jev-1.13.0 as the PRD states?

### Takeaway
Yes. On 2026-09-23, docs.typesafe.ai still documents `POST /v1/systemone`, Choice, Noul, independent parallel questions, Choice/Score confidence derived from the option distribution, Noul as a 0–1 probability with no separate confidence field, and `jev-1.13.0` as the version behind `jev-latest`. Pricing is still $0.042 per million input tokens with free output. The listed limitations still include literal reading, indirection, distracting context, and no guaranteed agreement between separate questions.

### Cited Findings
- The evaluation endpoint is `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer <API_KEY>` and `Content-Type: application/json`. The body is `state`, `model`, and a `questions` map. Each question key is returned on the matching answer and “is not sent to the underlying model and is not used in inference.” — [API reference](https://docs.typesafe.ai/api)
- Choice returns `choice`, `probabilities`, and `confidence`. Noul returns `noul` from 0 to 1. Score is a third primitive and returns `score`, `legend`, `probabilities`, and `confidence`. All three can be mixed in one call. Every question sees the same state and is evaluated independently, in parallel. One question’s answer is not context for another in that call. If a later question needs an earlier answer in order to build state or options, the docs say to make a second request. — [Introduction](https://docs.typesafe.ai/introduction); [Primitives](https://docs.typesafe.ai/primitives); [State](https://docs.typesafe.ai/concepts/state)
- Speculative fan-out is the documented pattern of asking questions that only matter for some inputs, then ignoring irrelevant answers in application code. The fan-out page says adding questions usually has little effect on response time. — [Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out)
- Choice and Score `confidence` is a 0–1 statistic computed from `probabilities`. The confidence page says a flatter distribution means lower confidence, that callers may threshold it, and that the right cutoff depends on stakes and on measured performance. Noul answers do not carry `confidence`. A Noul of 0.5 means yes and no are equally probable; it is not a medium score on a scale. — [Confidence](https://docs.typesafe.ai/confidence); [Primitives](https://docs.typesafe.ai/primitives)
- The confidence page’s three-option demo approximates confidence as `(3 × largest probability − 1) / 2` and says this approximates the general shape. The page says a cookbook of alternative computations is not linked yet. An API example shows Choice probabilities `{billing: 0.88, technical: 0.12, sales: 0.0}` with `confidence: 0.81`, so the documented confidence value is not identical to the selected option’s probability. — [Confidence](https://docs.typesafe.ai/confidence); [API reference](https://docs.typesafe.ai/api)
- The models page lists Jev 1.13 as `jev-1.13.0`. Price is $42 per billion input tokens / $0.042 per million input tokens. Output tokens are free. Stated limits: 250,000 tokens per second, 1,200 requests per minute, 64k tokens per request, and 32k tokens for `state` plus the longest question. Input is text only: string, JSON object, or array of text. No image, audio, or video. The page says rate limits can change without notice. — [Models](https://docs.typesafe.ai/models)
- `jev-latest` and `jev-preview` both point to `jev-1.13.0`. The page says there is no separate preview build right now, that aliases can move, and that a response’s `model` field reports the versioned ID. It says to pin a versioned ID when confidence thresholds were tuned against that version. API response examples use `"model": "jev-1.13.0"`. `GET /v1/models` lists aliases; versioned IDs are accepted by the `model` field whether or not they appear in that list. — [Models](https://docs.typesafe.ai/models); [API reference](https://docs.typesafe.ai/api)
- The jaggedness page applies to `jev-1.13` and says “Last reviewed 2026-09-17.” Failure modes named there: literal reading; unreliable counting and arithmetic; unreliable date and time comparison; extra indirection; accuracy loss when state contains irrelevant detail; adversarial text in state; contradictory instructions and criteria; no guarantee that a Noul and a yes/no Choice, or a Noul and its negation, agree; and no text generation. Worked numbers on that page: one ticket has Noul 0.22 beside a Choice of yes 0.01 / no 0.99 / confidence 0.97; another has refund Noul 0.72 and not-refund Noul 0.47, summing to 1.19. The page says not to carry a threshold tuned on a Noul over to a Choice. — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
- Jev is not fine-tuned or LoRA-adapted per customer. The same weights serve every account. Domain behavior is supposed to come from `state`, `instructions`, and `criteria`. English is the primary training language. Customer requests are not used for training, per the models page. — [Models](https://docs.typesafe.ai/models)
- The PRD states the same request shape, Choice/Noul split, independent questions, two calls when a later question needs the selected action, Choice confidence versus Noul’s lack of a confidence field, pin `jev-1.13.0`, and the literal-reading / indirection / distracting-context / structural-consistency limits. It also says the probe’s roughly `1 + participants × (2 + candidate tasks)` layout is evidence about that prototype, not the required production layout. — [PRD §5.1–5.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The probe’s question builder matches that prototype: one input-kind Choice, then per participant a recipient Choice, a timing Choice, and one dependency Noul per candidate task. Threshold constants are Choice confidence 0.80, Noul yes 0.85, Noul no 0.15. The default `--model` is `jev-1.13.0`. The endpoint constant is `https://api.typesafe.ai/v1/systemone`. — [probe_jev.py](file:///Users/moonmoon/Projects/t3code-rooms/scripts/probe_jev.py)
- The findings say the development fixture used three participants and two task candidates, hence 13 questions, and that those measurements were not rerun for the later action-catalog design. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- Reported research usage is 176,302 input tokens and 22,383 output tokens across 50 requests. At $0.042 per million input tokens and free output, 176,302 / 1,000,000 × 0.042 = 0.007404684, which the findings and PRD round to $0.007405. That price basis still matches the models page. This note did not re-sum the JSON reports or obtain an invoice. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md); [PRD §12](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [Models](https://docs.typesafe.ai/models)
- The YouTube oEmbed title is “How to Build Things with Jev & OpenJevs” (author name on the oEmbed payload: Sam Witteveen). The watch-page description text says the video builds a model router using “the API-based original Jev” and SemIf, and its timestamp list includes “11:47 Architecture” and “15:06 Running using SemIf.” No transcript was retrieved or used. — [Watch page](https://www.youtube.com/watch?v=ZR7anrL50xs); [oEmbed](https://www.youtube.com/oembed?url=https://www.youtube.com/watch?v=ZR7anrL50xs&format=json)
- A Vercel changelog entry dated 2026-09-21 describes a separate AI Gateway surface. It says an existing TypeSafe client pointed at the gateway keeps `choice` and `noul` shapes, while a new gateway HTTP integration uses the type name `boolean` and `POST /v1/evaluate` with model name `typesafe-ai/jev`. That is not the protocol on docs.typesafe.ai. — [Vercel changelog, 2026-09-21](https://vercel.com/changelog/ai-gateway-now-supports-typesafe-clients-and-http-api-for-jev)

### Inferences
- The PRD’s description of what hosted Jev can return for this product is still aligned with the official docs: a pinned `jev-1.13.0` call can classify a finite action list with Choice and score candidate yes/no edges with Noul, in one call when the questions do not need each other’s answers. It cannot emit the task text, invent task IDs, or execute a handler. Those limits follow from the generation failure mode and from the answer shapes, which stay inside the supplied options or a single probability.
- The PRD’s two-stage design matches the docs’ exception for dependent questions. Stage B can share a call when its options are already known. It needs another call when the selected action changes which candidates are legal. The earlier 13-question probe is the speculative-fan-out pattern, and the PRD already says irrelevant uncertain answers must not block a valid action.
- Nothing on the official pages reviewed shows a model newer than `jev-1.13.0` as of this fetch. Pinning `jev-1.13.0` rather than `jev-latest` is what the models page recommends once thresholds exist. The local thresholds were experimental, and the findings say they were not retuned on the action-first catalog.
- Calendar triggers are a poor fit for a single Jev judgment. The jaggedness page says date comparison is unreliable and that extraction, if used, should be closed Choices with the comparison done in code. That supports the PRD leaving calendar scheduling out of the interpreter.

### Gaps
- These pages were not byte-compared with a 2026-09-21 snapshot. Silent edits after that date are possible. The only explicit review date found on the limitation page is 2026-09-17.
- The confidence page does not publish a closed-form production formula outside the demo’s approximation. The exact function that produced the API example’s 0.81 was not independently derived here.
- `GET /v1/models` was not called. The models page’s statement that aliases currently resolve to `jev-1.13.0` was not re-checked against a live response.
- The YouTube description’s other timestamps were not treated as claims about what was said. No transcript was available, so the spoken walkthrough is not evidence.

## Does the documented environment variable name differ from JEV_API_KEY, and does the HTTP protocol care?

### Takeaway
Yes, the documented client variable is `TYPESAFE_API_KEY`, not `JEV_API_KEY`. The HTTP API only requires `Authorization: Bearer <API_KEY>`. The variable name is a local convention and is not part of the request.

### Cited Findings
- The Python SDK quickstart says to set `TYPESAFE_API_KEY` and then construct `TypeSafeClient()` with no key argument. — [Python SDK](https://docs.typesafe.ai/sdk/python)
- The models page’s curl example is `Authorization: Bearer $TYPESAFE_API_KEY`. — [Models](https://docs.typesafe.ai/models)
- The HTTP reference specifies the header `Authorization: Bearer <API_KEY>`. `401 Unauthorized` means the header is missing or invalid. The reference does not name an environment variable. — [API reference](https://docs.typesafe.ai/api)
- The probe reads `JEV_API_KEY` from the process environment or a local `.env` line and sends it only as the bearer token. The PRD says TypeSafe examples use a different variable name and that the HTTP protocol does not require renaming the local variable. It also says the credential stays in the service, not in a browser bundle, room message, or provider prompt. — [probe_jev.py](file:///Users/moonmoon/Projects/t3code-rooms/scripts/probe_jev.py); [PRD §5.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

### Inferences
- A room service can keep `JEV_API_KEY` and still speak the documented HTTP protocol, as the probe already does. Using the official SDK’s default constructor would require `TYPESAFE_API_KEY` or an explicit key argument. Those are client-library choices, not a change to what the API accepts.
- Renaming the local variable is unnecessary for protocol compatibility. It would matter only if the project switched to a client that reads `TYPESAFE_API_KEY` automatically.

### Gaps
- Official docs pages other than the Python SDK quickstart and the models-page curl example were not exhaustively searched for every SDK language’s variable name. Third-party SDK mirrors also document `TYPESAFE_API_KEY`, but they are not the TypeSafe docs site.

## Is SemIf actually a local semantic scorer without TypeSafe weights, and would it need a custom adapter?

### Takeaway
Yes. SemIf, formerly OpenJev, scores options with open checkpoints it does not claim are TypeSafe weights. Its documented interface is a local scorer and a browser lab, not `POST /v1/systemone`. A room adapter would have to translate action and reference questions into SemIf rows and would have to evaluate its own thresholds. The repo’s README gained PyTorch/MPS scoring, a 27B EXL3 bridge, and per-workload temperature calibration on 2026-09-22; none of that removes the adapter requirement, and this repository has not run SemIf.

### Cited Findings
- The README title is “SemIf (formerly OpenJev).” It says the project is independent and not affiliated with or endorsed by TypeSafe, and that it “does not reproduce Jev's undisclosed model or training.” Model weights are not in the repository. — [SemIf README](https://github.com/TheoLeeCJ/SemIf/blob/master/README.md)
- The documented input row is `{id, state, question, options: [{id, description}, ...]}`. Returned probabilities “are conditional on the supplied options.” The README says to calibrate and validate them on the workload where they will make decisions. The quick start is the `semif-score` command with `--mode direct`, `--model Qwen/Qwen3.5-4B`, and a pinned revision, reading JSONL. Shared mode prefills one exact state and scores many criteria. There is no documented TypeSafe HTTP route in that README. — [SemIf README](https://github.com/TheoLeeCJ/SemIf/blob/master/README.md)
- README “Latest changes,” dated 2026-09-22: PyTorch/MPS scoring for Apple Silicon; a Qwen3.8-27B EXL3 bridge; per-workload temperature calibration. Calibration “does not change the selected option.” An earlier 2026-09-18 note adds browser models and an “Unsloppify” interface. Apple Silicon instructions say native MLX is for macOS arm64 via `pip install -e '.[test,mlx]'` and `--backend mlx`, with PyTorch/MPS as another path. — [SemIf README](https://github.com/TheoLeeCJ/SemIf/blob/master/README.md)
- `mlx_backend.py` requires Darwin on arm64 and Metal, loads native Qwen3.5 text checkpoints only, and labels each result `"probability_status": "conditional option score; uncalibrated as decision confidence"`. The readout is last-position logits restricted to declared answer slots, with no generated tokens. The module docstring says scores remain conditional on the declared options, not calibrated confidence. — [mlx_backend.py](https://github.com/TheoLeeCJ/SemIf/blob/master/src/semif_phase1/mlx_backend.py)
- The browser README describes a static WebGPU page with no API, database, telemetry, or server-side inference. First load downloads a GGUF of 639 MB, 1.56 GB, or 3.01 GB depending on tier. Direct probabilities “are conditional on only the displayed label tokens,” “are not calibrated probabilities,” and “a high value does not establish that the underlying decision is correct.” The balanced-accuracy figures shown in the setup panel are from native BF16 checkpoints, not from the quantized browser artifacts. The Jev comparison number is described as TypeSafe’s published subset result; the page says no live Jev endpoint was used. — [Browser demo README](https://github.com/TheoLeeCJ/SemIf/blob/master/webgpu-demo/README.md)
- On SemIf’s own table, Qwen3.5-4B native BF16 modal agreement with published Jev on a 102-row public subset is 0.845, against published Jev’s 0.883 on that subset. The README says the comparison was not a live Jev run and is not TypeSafe’s 711-row aggregate. Authored-decision balanced accuracy for the 4B direct-logit baseline is 0.813 on 144 rows. Those figures are SemIf’s workloads, not T3 Rooms instructions. — [SemIf README](https://github.com/TheoLeeCJ/SemIf/blob/master/README.md)
- The PRD already says SemIf needs a room adapter, is not a drop-in for the Jev HTTP endpoint, that local scores must not be forced into Jev’s confidence representation, and that no SemIf installation or local inference benchmark was done in that review. It cites the MLX backend and the browser README. — [PRD §5.0](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The video description, not a transcript, identifies a model-router demo that uses hosted Jev and SemIf, with architecture at 11:47 and SemIf at 15:06. The PRD says the transferable idea is separating decision selection from execution, and that the product should not switch a participant’s harness or model because that demo routes prompts between models. — [Watch page](https://www.youtube.com/watch?v=ZR7anrL50xs); [PRD §5.0](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

### Inferences
- A custom adapter is required. SemIf’s row is one question plus an option list. Jev’s request is a map of typed `choice`, `score`, and `noul` questions, and Choice confidence is a separate field that Noul does not have. Mapping room actions onto SemIf options, and mapping a dependency onto a two-option or logit score, is application code. The PRD’s 0.80 / 0.85 / 0.15 gates are Jev-probe settings and are not SemIf outputs.
- MLX can run on Apple Silicon for Qwen3.5, which matches a local optional scorer, but only inside that backend’s constraints: arm64, Metal, pinned Qwen3.5 text weights, and scores the module itself calls uncalibrated. The 2026-09-22 MPS path is another local runtime, not a Jev-compatible server. The browser demo cannot sit behind the durable queue: it is a page that downloads weights and does not expose server-side inference.
- SemIf’s published agreement with Jev on 102 public rows is evidence about SemIf’s benchmark, not evidence that SemIf would route T3 room commands. The PRD’s requirement to test the room’s own action and reference set before enabling local suggestions is still unmet in this repository.

### Gaps
- This pass did not inventory every SemIf file for an undocumented HTTP server. The README, MLX backend, and browser README do not describe a `systemone` drop-in.
- SemIf was not installed or scored on the room fixtures. Quality numbers above are the project’s published tables, not a local rerun.
- Whether the 2026-09-22 README entries were already visible when the PRD paragraph was drafted is not recorded in the PRD. They are visible on `master` as of this fetch and are newer than the 2026-09-21 experiment date.

## Given the local results, does the evidence support shipping unattended natural-language routing?

### Takeaway
No. The PRD’s refusal of unattended natural-language routing matches the local evidence. The final combined system matched 21 of 28 author-labeled outcomes and, among plans it was willing to act on, matched 13 of 13 fixture expectations. It also withheld a correct plan on 6 of 19 runs that were expected to be actionable, changed its mind across repeats, and needed a code guard to stop a confident wrong prerequisite. That supports an optional, editable suggestion layer later. It does not support letting free-form text dispatch work with no person and no deterministic controls.

### Cited Findings
- Final v3 development exact outcomes: 14/16. Held-out phrasing, two repeats each: 7/12. Combined: 21/28. All 50 requests completed with no recorded HTTP, transport, or schema error. Median latency on the v3 development run was 600.39 ms; on the holdout, 634.78 ms; across all calls, 613.60 ms. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- Of 19 runs expected to produce an actionable plan, 13 did, and all 13 matched the fixture’s recipients, timing, and prerequisites. Six of those 19 asked for clarification instead. One further mismatch, the quoted-command case, asked for clarification instead of treating the message as a note. Those seven inexact runs are what PRD §12 summarizes as “seven other runs unnecessarily requested clarification.” The 13/13 figure is the plans that cleared the gates, not 13/13 of all cases and not 13/19 of the cases expected to be actionable. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md); [PRD §12](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Holdout repeats were not stable. “Busy sol1 gets an explicit new task now,” “Dependency clause comes before `@sol2`,” and “Leave it on hold until I say go” were each an unnecessary clarification on one repeat and a correct plan on the other. “Reviewer checks after authentication architecture is complete” was an unnecessary clarification both times. “Unknown alias `sol10`” was a correct clarification both times. The voice-style review phrasing was a correct plan both times. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- In v2, `@sol2 review once it is done` selected `task41` with dependency Noul 0.87 even though two tasks were possible and no antecedent was identified. The unguarded interpreter accepted that plan. In v3, Jev still preferred `task41`, and a lexical code check forced clarification. The findings call that check an illustrative guard, not a complete reference resolver, and say confidence alone was insufficient. The expected outcome for that case was clarification, so the code-enforced result counts inside the 14/16, not as a model success at resolving “it.” — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md); [probe_jev.py](file:///Users/moonmoon/Projects/t3code-rooms/scripts/probe_jev.py)
- The findings say the samples are small and author-labeled, that zero incorrect actionable plans on the final runs is not a calibrated error rate, that the holdout was not an independently labeled or blinded evaluation, and that questions and thresholds were not changed using the holdout. They also say the measurements “must not be presented as validation” of the action-first design because they were not rerun for it. The closing sentence says free-form interpretation is not ready to run unattended, and that the experiment does not establish unrestricted natural-language sequencing. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- The PRD puts hosted Jev and local SemIf in Phase 2, after a useful room exists. It says the results “support investigation of assistance, not unrestricted unattended natural-language routing,” and that they do not validate the revised action-first mapping. Accepted work is committed by the user through the same validator as manual input. On a Jev error, the draft is preserved and a conditional request must not become an immediate send. A queued task then runs without further Jev calls. “100% Jev accuracy” is explicitly not a product promise. — [PRD §5.0, §5.4, §10, §11, §12](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Not tested, per the findings: a real T3 adapter, queue persistence, retries, restart, prospective task nodes from a compound sentence, calendar conditions, “after either,” alias pools, a large roster, audio, multilingual accuracy, summarization, cancellation target resolution, and permission-response workflow. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)

### Inferences
- The PRD’s reading is confirmed. Unattended routing would treat a natural-language message as a dispatch decision without a person confirming the draft. The local system refused or missed that standard on the six expected-actionable clarifications, on repeat flips, and on the pronoun case, where only the code guard prevented a wrong prerequisite from shipping. A perfect 13/13 among the plans that survived the gates does not cover the runs that should have produced a plan and did not, and it does not cover the model’s wrong preference on the ambiguous pronoun.
- The appropriate product use of this evidence is the one the PRD already states: keep direct controls as the way work is sent, and treat Jev as an optional drafter whose output stays editable and is re-checked in code. Enabling that drafter still requires a new evaluation on the action-catalog questions. This sample does not supply that evaluation.
- Some of the six misses are described as policy composition, not only model error: uncertainty about a participant who should not receive work can block the whole message. That still blocks unattended dispatch, because the user would not get the plan the fixture called correct.

### Gaps
- The raw JSON result files were not re-scored in this pass. Counts above are the findings’ published tables.
- No separate inter-annotator label exists, so “exact match” means match to the author’s fixture, not match to an independent judge.

## Is the proposed 95% / 100-instruction gate something the current sample can satisfy?

### Takeaway
It cannot. The gate asks for an independently reviewed set of at least 100 representative instructions, at least 95% exact suggestions on clear in-scope commands, and no confidently wrong recipient or prerequisite suggestion in that acceptance run. The current evidence is 22 author-written instructions, 28 runs, a combined exact-outcome rate of 21/28 (75%), a development rate of 14/16 (87.5%), and a holdout rate of 7/12 (58.3%). It is not independently reviewed, it is not the action-first mapping, and it already contains a confident wrong prerequisite at the model layer.

### Cited Findings
- The PRD’s proposed gate, for each enabled Jev mapping: “on an independently reviewed set totaling at least 100 representative instructions, at least 95% exact suggestions for clear in-scope commands and no observed confidently wrong recipient/prerequisite suggestion in the acceptance run.” It also says to report sample size and uncertainty, that passing a finite set does not guarantee future correctness, and that a confidence threshold is not itself the quality metric. Mappings that miss the gate stay disabled while the direct controls remain. The same section says the synthetic probe is feasibility evidence for an earlier question layout, not a production reliability benchmark, and not evidence about SemIf. — [PRD §11](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Observed exact-outcome counts from the findings: development 14/16, holdout 7/12, combined 21/28. Unique messages are the 16 development cases plus 6 new holdout phrasings. The holdout repeated each of those 6 twice, which is why there are 12 holdout runs and 28 runs overall. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- 15/16 = 93.75%, which is still under 95%. The development set would need 16/16 to clear a 95% bar on those 16 items alone. It has 14/16. The combined runs would need at least 27/28 to reach 95% (because 0.95 × 28 = 26.6). They have 21/28. The holdout would need at least 12/12 (0.95 × 12 = 11.4; 11/12 = 91.7%). It has 7/12. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md); [PRD §11](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The findings say the holdout “does not meet the PRD's proposed release gate,” that expectations were authored by the same effort that wrote the questions, and that the result is not an independently labeled or blinded evaluation. They also say the action-first design was not measured. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- v2 accepted a wrong `task41` prerequisite at Noul 0.87, which is above the probe’s 0.85 yes threshold. v3 still had Jev prefer `task41` on the ambiguous pronoun; code, not the model score, produced the clarification. — [JEV_FINDINGS.md](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md); [probe_jev.py](file:///Users/moonmoon/Projects/t3code-rooms/scripts/probe_jev.py)

### Inferences
- Sample size alone fails the gate. Twenty-two instructions, or 28 runs if repeats are counted separately, are below 100. A hypothetical 28/28 on this file would still miss the size requirement.
- Every reported slice misses 95% as a fraction of that slice. The most favorable published slice, 14/16, is 87.5%, and even 15/16 would still be 93.75%. There is no rounding of these counts that produces a 95% pass.
- The “no confidently wrong suggestion” clause is already breached in this sample if “suggestion” means the model’s prerequisite preference: Noul 0.87 on the wrong task in v2, and the same preference still present in v3 before the code guard. If the clause means only the plan emitted after the guard, v3 did not emit that wrong plan, but v3 is still the wrong question layout, the wrong sample size, and not an independent acceptance run. Either reading leaves the gate unsatisfied.
- A Wilson 95% interval computed here from the published 21/28 count, not from a paper, is about 0.57 to 0.87. The upper end is still under 95%. The development-only interval is wide enough that its upper end can sit near 95% only because n=16 is small. That width is a reason the PRD asks for 100 instructions and an uncertainty report. It is not a pass.
- The six unnecessary clarifications matter even under a gate aimed at “clear in-scope commands.” Several holdout failures are explicit assignments or explicit holds, not the ambiguous-pronoun case. The sample was not pre-split into a “clear command” subset of 100, so it cannot be re-labeled into a passing gate after the fact without a new review.

### Gaps
- The gate’s phrase “exact suggestions for clear in-scope commands” was not given a separate labeled subset in the fixtures. This note does not invent one.
- No new 100-instruction set exists in the repository from this review.

## What product capabilities do not depend on Jev?

### Takeaway
Phase 1 does not depend on Jev or SemIf. Direct controls, the explicit command grammar, validation, the durable queue, dependency release, notes, and T3 session attachment are specified to work with inference disabled, with no Jev key, and with no local classifier. Jev is limited to optional candidate fields for a finite action and known IDs. It does not define the catalog, write the instruction, or run the task.

### Cited Findings
- The PRD’s input-mode table assigns direct controls and explicit syntax to the first release with model requirement “None.” Local SemIf and hosted Jev are optional later. The implementation order is action catalog and handlers, then complete direct controls, then deterministic command validation and scheduling, then optional adapters. “Jev does not define product capabilities or receive a separate execution path.” — [PRD §5.0–5.1](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Phase 1, with no interpreter required, lists: the versioned action catalog, preconditions, handlers, and direct controls; one local T3 environment; named participants; shared timeline; explicit recipient and timing controls; preserved room notes; exact alias and command parsing into an editable draft with no model call; dependencies on existing tasks, including waiting for both; manually held tasks; edit, cancel, and release; pending-input and error visibility; a persistent SQLite queue and outbox; reconnect reconciliation; context delivery; agent-managed workspaces; and links back to native T3 sessions. — [PRD §10](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The Phase 1 acceptance table requires every catalog action and the participant and native-request controls to work “with inference disabled, no Jev key, and no local classifier installed.” Explicit syntax and direct controls share a handler. Contract checks reject unknown actions, bad enums, missing references, cycles, stale revisions, and illegal transitions before execution. Exact aliases, explicit commands, incomplete syntax, and missing task references must produce the specified drafts or errors without a model. — [PRD §11](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The first-release command examples are exact, not paraphrase: `@sol2 review the diff` for a Now draft, and `/after task41 @sol2 review the implementation` for an After-task41 draft. Only the defined syntax is interpreted. Task text stays verbatim. Invalid commands remain drafts. The GUI is how every action is expressed without the syntax. — [PRD §5.0](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Once a task is accepted, it runs without further Jev calls or continued Jev availability. Jev cannot invoke a command handler. Compound sentences that create new tasks and edges inside one message are Phase 2; until then the PRD says to show two assignment cards rather than execute the sentence as parallel work. Jev “cannot generate arbitrary instruction strings or invent these IDs.” The probe does not test that construction. — [PRD §5.4–5.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Docs say `jev-1.13` is not trained to generate text, that forcing generation by chaining choices “will not work well,” and that bounded extraction should be a Choice over options produced elsewhere. They also say to keep arithmetic and date comparison in code, and that questions in one call cannot read sibling answers. — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13); [Primitives](https://docs.typesafe.ai/primitives)
- The browser SemIf demo has no server-side inference. The PRD says the durable queue must continue with neither model running and with no browser open. — [Browser demo README](https://github.com/TheoLeeCJ/SemIf/blob/master/webgpu-demo/README.md); [PRD §5.0](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

### Inferences
- Shipping the room the PRD calls useful does not wait on Jev, SemIf, a key, or a passing 95% gate. Those are switches for suggestion quality after the catalog and queue already work.
- Capabilities that stay outside both models, given the current docs and the PRD boundary: choosing recipients and timing from controls; parsing only the documented grammar; storing and retrying tasks; releasing a dependent task when the recorded predecessors complete; fan-in; holding, editing, cancelling, and releasing; showing notes; attaching named T3 sessions; and forwarding artifact locations. None of those need a probability.
- Capabilities Jev specifically does not add, even if Phase 2 turns it on: rewriting the user’s instruction, summarizing a session, inventing dependency IDs, creating prospective tasks from a compound sentence by itself, comparing calendar times, transcribing audio, or replacing the queue when the API is down. SemIf does not add those either. Its documented job is local option scoring.

### Gaps
- Phase 1 is a requirements list. This note does not show that any of those controls are implemented in the repository.
- Section 4’s full control inventory was not re-read line by line beyond what sections 5, 10, and 11 repeat. The independence claim follows those sections, not a UI audit.
