# T3 Rooms Phase 1 spec completeness

Documentary re-check of whether the draft PRD (updated 2026-09-22) specifies Phase 1 well enough to implement as ordinary application code without inventing product rules that change stored graphs or user-visible behavior. Primary sources: `PRD.md` and the local assessments. No software was implemented. The Jev API was not called. T3 was not mutated. Closed T3 PRs are not treated as shipped capabilities.

**Overall distinction (used throughout):** *Can start building* means an engineer can code the catalog happy path, `after_all` on existing task revisions, a frozen briefing, and SQLite persist-before-send against a fake adapter, using sections 4.4–4.5, 6.1–6.3, 6.5, and 7. *Can claim Phase 1 complete per section 11* means two implementers would persist the same task graph under cancel/edit/retry/restart, every catalog-plus-native control would have a handler, and the live harness rows would have a defined correlation contract. The first is largely true. The second is not.

**Position on earlier notes.** This review **agrees** with [product-shape.md](file:///Users/moonmoon/Projects/t3code-rooms/research_notes/T3%20Rooms%20plan%20feasibility/product-shape.md) on missing command schemas, undrawn transitions, the section 1 vs 5.5 split, and optional Jev/SemIf/summarizer. It **refines** that note’s binary “not specified enough to implement Phase 1”: the missing pieces block a section 11 completion claim, not a start. It **disagrees** with [IMPLEMENTATION_ASSESSMENT.md](file:///Users/moonmoon/Projects/t3code-rooms/research/IMPLEMENTATION_ASSESSMENT.md) lines 7–8 (“The plan is implementable as specified”) as a Phase 1-complete claim: that assessment shows T3 surfaces exist and Jev is optional, but its “gaps before coding” list omits graph-identity rules that change persisted tasks. Adapter findings in IMPLEMENTATION_ASSESSMENT and [t3-contracts.md](file:///Users/moonmoon/Projects/t3code-rooms/research_notes/T3%20Rooms%20plan%20feasibility/t3-contracts.md) are cited where they bear on untested mapping; this pass did not re-open T3 source.

There is still no JSON Schema, SQL DDL, or transition appendix in the repo besides the PRD. Local JSON files are Jev fixtures/results only.

## Is Phase 1 specified enough to build the action catalog, command schema, state machine, dependency rules, delivery contract, and restart/outbox?

### Takeaway

The durable-queue *happy path* is specified enough to start building as ordinary code: nine catalog operations, three schedule modes, revisioned `after_all`, cycle rejection, frozen briefing, persist-before-send. It is **not** specified enough to claim Phase 1 complete per section 11 without inventing command fields, recovery transitions, retry identity, and participant/native schemas. Those inventions change behavior.

- Section 4.4 tables nine operations: `task.create` with timing `now` / `after_all` / `manual`; `room.note.create`; `task.update`; `task.release`; `task.cancel`; `task.interrupt`; `task.retry`. Each row lists required fields, a direct UI control, and a result sentence. — [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- “Review” is an instruction, not a command. “Review now,” “review after task 41,” and “save a review for later” share `task.create` and differ only by timing. — [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The same section says participant creation/attachment, renaming, binding changes, room creation, and answers to native harness questions/permissions have direct forms, do not depend on Jev, and sit “outside its initial selectable action subset.” It names no command types or fields for them. Rebinding is subject to the outstanding-task rule in 4.2. Answering a native permission request “uses the options reported by T3.” — [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Phase 1 still requires those extra controls: create/attach named participants, optional persona briefs, pending-input and error visibility. Section 11’s first row requires “every action in the catalog **and** all participant/native-request controls” with inference disabled. — [PRD §10](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §11](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

**Command schema**

- Discriminated-union rule: `now` and `manual` do not accept prerequisite fields; `after_all` requires a nonempty list. Unknown names, invalid enums, nonexistent references, unsupported fields, and stale revisions fail before execution. — [PRD §4.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The prose calls this a “versioned command.” The example has no version field. Section 6.1’s Room record has “next event sequence,” not a room revision. Participant records have a binding generation. Task, draft, and interpretation each have their own revision. The text never equates these tokens. — [PRD §4.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §6.1](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- `instruction` stays user-authored text or a selected verbatim source span. Aliases resolve to stable participant IDs. There is no JSON example for `task.update`, `task.release`, `task.cancel`, `task.interrupt`, `task.retry`, `room.note.create`, participant/binding commands, or a native-permission response. `task.retry` requires “explicit dependent-task handling” with no enum. — [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §4.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

**State machine**

- Composer states `action_draft`, `needs_interpretation`, `needs_clarification` are not tasks. A task is created only on valid submit. Direct UI reaches the queue without a Jev state. An unresolved draft authorizes no partial dispatch. — [PRD §6.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Drawn task edges: `held → queued` on release; `queued → dispatching` when prerequisites are satisfied and the assignee is available; `queued → blocked` when a prerequisite fails or the binding is unavailable; `dispatching → running` when T3 accepts and starts a correlated turn; `running → needs_input → running`; `running → succeeded | failed | interrupted`; `queued → cancelled`; `held → cancelled`; `blocked → queued` when the user resolves the blocker. — [PRD §6.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- `queued` has a visible reason: waiting for named tasks, waiting for the assignee, or ready. Manual hold is distinct from dependency waiting. — [PRD §6.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- The diagram has no edge out of `dispatching` except `running`; no edge out of `failed` or `interrupted`; no user “mark blocked” edge; no `task.retry` edge; no restart/reconciliation loop. — [PRD §6.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §6.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

**Dependency rules**

- Bind to specific task revisions, not “alias becomes idle.” Initial semantics are wait-for-all. “After either” is out of scope. Already-successful prerequisites add no wait. Failure, interruption, or unresolved native input does not release dependents. A new attempt is an explicit user operation; the system records whether dependents reattach. — [PRD §6.3](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- One room-dispatched turn at a time per participant. Different participants may run concurrently within provider capacity. The service owns the wait and must not send the review early for the agent to poll. — [PRD §6.3](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Submit-time checks in 5.4 (even though 5.x is the optional-interpreter chapter): references belong to this room; UI selections beat inferred ones; a prerequisite mention does not make that participant a recipient; every dependency needs an explicit task/author/topic reference or an unambiguous selection; `send_after` maps to nonempty `after_all`; “now” plus prerequisite edges is invalid; no self-edge or cycle; fan-in keeps every requested predecessor; unresolved candidates are not dropped; the roster/task snapshot is re-checked at save. — [PRD §5.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Cancel of work T3 has not accepted must “expose the resulting block on dependent tasks.” The diagram’s `queued → blocked` trigger is “prerequisite fails or binding unavailable,” not cancellation. — [PRD §4.4](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §6.2](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

**Delivery contract**

- At dispatch: freeze a room sequence cutoff; gather shared messages this binding has not received and does not already own; include prerequisite results and reported file/branch/commit/artifact references; append the current assignment separately; save the exact briefing and source event IDs before sending. — [PRD §7](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Parallel tasks released together share one initial cutoff. A review assembles its briefing only when released. In-progress streaming text is UI-visible and is not injected into another running session. — [PRD §7](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Unseen visible messages are kept while they fit “the delivery budget.” Over budget, condensation is shown, source references are kept, and originals stay accessible. A generative summarizer is optional. The budget size, condensation algorithm, and a “user-pinned decisions” action are not defined. — [PRD §7](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Delivery record fields: task/run ID, exact briefing, included event IDs/sequence range, command ID, acceptance state. The room keeps original history; native history is not rewritten. Agent replies do not create work. — [PRD §6.1](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §7](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)

**Restart and outbox**

- SQLite is required for transactional tasks and an outbox. A JSON log is “sufficient for a disposable conversation demo” and insufficient for restart-safe dispatch. — [PRD §6.1](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Persist the task and dispatch intent before external submission. Use a stable T3 command ID for an identical retry; store the exact briefing so a retry does not rebuild it with newer context while reusing that ID. After reconnect, reconcile accepted commands and correlated turns before another dispatch. Bookkeeping advances on confirmed acceptance, not on prepare, and not on an HTTP acknowledgement. Editing a pending instruction creates a new revision and command identity. UI closure does not stop the service. Offline time does not run jobs. — [PRD §6.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- No outbox columns, lease, or `dispatching` recovery transition are specified. Section 6.5 does not say whether one `task.create` with several recipients is one command ID or one ID per created task. — [PRD §4.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [PRD §6.5](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md)
- Phase 0 “does not start T3 sessions, test the scheduler against real harnesses, or build the room interface.” The Jev study did not test queue persistence, retries, restart recovery, or completion correlation. — [PRD §10](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md); [Jev findings, Not tested](file:///Users/moonmoon/Projects/t3code-rooms/research/JEV_FINDINGS.md)
- IMPLEMENTATION_ASSESSMENT’s recommended build order is adapter spike → SQLite scheduler with fake adapter → UI → two-harness acceptance. That is engineering advice, not a PRD schema. — [IMPLEMENTATION_ASSESSMENT.md](file:///Users/moonmoon/Projects/t3code-rooms/research/IMPLEMENTATION_ASSESSMENT.md)

### Inferences

- An engineer can start the deterministic core from sections 4.4, 4.5, 6.1, 6.3, and the five dispatch steps in section 7, then unit-test it against a fake adapter. The catalog table plus the three schedule modes is a real command surface.
- Claiming section 11 complete requires more than that core. Participant/native commands, mark-blocked, `dispatching` recovery, cancel-to-dependent transitions, and the meaning of “identical retry” versus `task.retry` are product rules the prose requires and does not define. Those remain even if an adapter can create threads, submit turns, and report correlated completion.
- “Versioned command” and “room revision” are words without a wire or storage definition. Implementers will pick an optimistic-concurrency token. Section 11’s “stale revisions” test cannot be written unambiguously until task revision, room/event sequence, binding generation, and draft revision are distinguished.
- **Disagreement with IMPLEMENTATION_ASSESSMENT lines 7–8:** “implementable as specified” is true for *starting* the fake-adapter queue and for “no model required.” It is not true that the specification already determines the persisted graph under retry, cancel, edit, mark-blocked, and restart. That assessment’s pre-coding list (stack, rewrite 6.4 event names, auth, persona, PR refs, git, direct-activity) does not include those graph rules. — [IMPLEMENTATION_ASSESSMENT.md](file:///Users/moonmoon/Projects/t3code-rooms/research/IMPLEMENTATION_ASSESSMENT.md)
- **Refinement of product-shape.md:** that note’s “not specified enough to implement Phase 1 as accepted in section 11 without inventing…” is correct as a *completion* claim and too strong as a *start-coding* claim. The rest of its catalog/schema/machine inventory re-verified against the PRD and stands.

### Gaps

- No field-level schema for any command except one `task.create` / `after_all` example.
- No enumerated values for `task.retry`’s “explicit dependent-task handling.”
- No definition of “assignee available” beyond one room-dispatched turn plus section 9’s warning about direct T3 activity.
- No delivery-budget number, pin action, or condensation procedure.
- No SQL for the outbox and no crash matrix (before send, after send before ack, after ack before `running`, duplicated process).
- No command or fields for participant create/attach/rename/rebind, room create, native permission response, or mark-blocked.

## Where is the spec contradictory, underspecified, or dependent on untested adapter behavior?

### Takeaway

The contradictions that can ship the wrong Phase 1 are: natural-language examples in 4.3 against the Phase 1 parser limit; the state diagram against retry/cancel/restart; “mark blocked” / “dependents blocked” against a diagram that never defines those transitions; and 6.4 “first release” mark-blocked against Phase 2 “explicit task-outcome reporting.” Section 12’s five adapter spikes remain open in the PRD. IMPLEMENTATION_ASSESSMENT claims several T3 surfaces exist; that is adapter evidence, not a closed product spec, and it conflicts with t3-contracts.md on whether `turn-diff-completed` is the success signal. Closed PRs #12457, #9181, and (per IMPLEMENTATION_ASSESSMENT) #12148 are unmerged and are not capabilities.

## Can the stated user story in PRD section 1 be implemented with the Phase 1 rules, including the section 5.5 compound-sentence limit?

### Inferences

- **D1 — two implementers, three graphs.** (A) `task.retry` reuses the T3 `commandId`: if the first attempt was accepted, T3 replays the old receipt (t3-contracts) and no new attempt runs; dependents may wait forever or follow a dead revision. (B) `task.retry` mints a new command ID and a new **run** on the same task ID/next revision; dependents reattach only if the user enum says so. (C) `task.retry` creates a **new task ID**; old edges still point at the failed id. Section 6.3 wants (B)-like recording of reattachment; section 6.5’s “identical retry” is a different operation (outbox resend). These must be two named operations, not one word. The dependent-handling enum (reattach / leave-on-old / block) must be persisted on the retry command. **Must decide before coding.**
- **D2 — cancel.** (A) Cancel prerequisite → dependents `queued → blocked` with reason. (B) Dependents remain `queued` with reason “waiting for named tasks” (zombie wait). (C) Cascade `cancelled`. 4.4’s “expose the resulting block” argues for (A), but the diagram does not. Section 11 will not catch (B) vs (A). **Must decide before coding.**
- **D3 — edit.** Because edges bind to a revision, (A) leave dependents on revision 1 after an update to revision 2 (revision 1 never succeeds → stuck); (B) auto-retarget to 2; (C) move dependents to `blocked` until the user reattaches. Add-follow-up’s “exact task/revision” implies retargeting is **not** silent. Two implementers who pick (A) vs (B) persist different prerequisite tuples on the same review. **Must decide before coding.**
- **D4 — mark-blocked.** (A) Omit until Phase 2 (violates 6.4; matches 10’s Phase 2 bullet). (B) New command from `succeeded` → treat as failed for dependents still `queued`; no-op if dependents already `dispatching`/`running` (4.3: cannot retract accepted work). (C) Also interrupt already-dispatched dependents. Without (B) or (C) specified, a “successful” prose-blocker releases the review exactly once — the sequential-review row can pass while the user-visible product is wrong. **Must decide before coding** if 6.4 is Phase 1.
- **D5 — dispatching.** Crash after persist, before send: identical resend of the same command ID and frozen briefing (6.5) is the only specified recovery; stay-in-`dispatching` until ack. Crash after send, unknown ack: same identical resend (T3 receipt replay makes this safe **if** body matches; t3-contracts says body is not compared — so the frozen briefing is mandatory). Crash after ack, before `running`: identical resend should no-op at T3; the room must not mint a new command ID. Implementer who marks `failed` and waits for `task.retry` will create a second attempt and can duplicate work if the first turn still starts. **Must decide** the `dispatching` crash matrix, including T3 rejection (new identity required).
- **D6 — concurrency tokens.** (A) `roomRevision` = event sequence; any new timeline event stale-fails in-flight commands. (B) Separate monotonic room revision, bumped only on roster/task-graph changes. (C) Task commands check only `task.revision`; room revision is ignored. Binding generation must stale-fail a command that targets a rebound participant (4.2 outstanding-task rule). Draft revision is composer-only. Interpretation `state revision` is Phase 2. Two implementers who mix (A) and (C) will reject different submits and persist different “stale” errors; section 11’s stale-revision test has no single oracle. **Must decide** which token each command type checks.
- **Also decide (graph-affecting, slightly narrower than D1–D6):** multi-recipient create = N task rows and N T3 command IDs (recommended by independent-assignment wording, not written); `needs_input` on predecessor → dependents stay `queued` with visible reason **or** move to `blocked` (11 vs 6.2); rebind algorithm for outstanding tasks; whether T3-direct activity counts as “assignee unavailable.”
- IMPLEMENTATION_ASSESSMENT’s “choose the stack / rewrite 6.4 event names / record auth” are real engineering and adapter issues. They do **not** substitute for D1–D6. Two TypeScript implementers can still persist different graphs. **This is the main disagreement with IMPLEMENTATION_ASSESSMENT’s “gaps to close before coding.”**
- **Agree with product-shape.md** that superseded revisions plus `task.retry` reattachment are where two careful implementers diverge, and that section 11 lacks rows for “edit prerequisite revision” or “cancel versus fail.”
