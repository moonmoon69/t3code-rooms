# Start the queue, freeze six rules
**Phase 1 of T3 Rooms is implementable as ordinary application code without forking T3 and without Jev, SemIf, or Herdr, under two conditions: the six graph-identity rules below are written before any scheduler that persists tasks, and this Mac’s T3 server is switched to a pairing-capable policy before any live adapter spike.** An engineer can start the catalog, SQLite queue, and room UI against a **fake adapter now**. They cannot claim Phase 1 complete per PRD section 11 until those six rules exist as command fields and transitions, participant and native-request handlers exist, and two real harnesses have shown correlated completion. Three things are **not implementable yet as specified**: unattended natural-language routing, the section 1 compound utterance as one command, and Desktop-only authentication against the Nightly already running on `127.0.0.1:3773` without a user-visible pairing change. The earlier headline that “the plan is implementable as specified” is true for T3 surfaces and for “no model required”; it is false as a section 11 completion claim. Do not implement Jev in Phase 1.

## Direct HTTP covers the adapter; this Desktop does not pair
Every Phase 1 control operation already exists on T3’s public client commands and HTTP/RPC: `thread.create`, `thread.turn.start`, `thread.turn.interrupt`, `thread.approval.respond`, `thread.user-input.respond` / `dismiss`, `thread.runtime-mode.set`, `thread.interaction-mode.set`, shell and per-thread snapshots, and `orchestration.subscribeThread`. There is **no `thread.attach` command**; attach is bind-by-id from `GET /api/orchestration/shell` or `subscribeShell`. Full conversation `message.text` is returned from the official per-thread GET when `turnLimit` is omitted; the 8,000-character cap belongs to community `t3code-thread-mcp`, not to T3. Client-supplied `commandId` is a durable idempotency key: an accepted receipt is replayed as `{ sequence }` **without comparing the new body to the original**, so a changed briefing under a reused id is silently ignored. HTTP `POST /api/orchestration/dispatch` does **not** run WebSocket `bootstrap.createThread`; a companion using HTTP must send `thread.create` then `thread.turn.start`. Native `/mcp` on the same port is a provider-scoped in-session toolkit, not a companion control plane. Closed PRs are not the path: **#12148** (desktop connection bridge for local tools) was closed unmerged on 2026-09-19 after Julius noted a V2 rewrite of orchestration/provider layers; **#12457** and **#9181** are also closed unmerged and do not grant third-party access. Pin the adapter to the connected `serverVersion` and `orchestrationProtocolVersion` and fail closed on mismatch. ([orchestration.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/packages/contracts/src/orchestration.ts), [environmentHttp.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/packages/contracts/src/environmentHttp.ts), [http.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/apps/server/src/orchestration/http.ts), [ws.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/apps/server/src/ws.ts), [OrchestrationEngine.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/apps/server/src/orchestration/Layers/OrchestrationEngine.ts), [PR 12148](https://github.com/pingdotgg/t3code/pull/12148), [t3code-thread-mcp README](https://github.com/samdickson22/t3code-thread-mcp/blob/391b9a783c3e62dfa3ca948b4835efb3473d6ab4/README.md))

The no-fork pairing path is: install the CLI (`curl -fsSL https://t3.codes/install.sh | sh`), then choose **one** pairing-capable mode. Preferred for a same-machine companion is `t3 serve` or `t3 service install`, which should yield **`loopback-browser` with `one-time-token`** (the macOS service **stops at logout**). The alternative that keeps Desktop as the server is Settings → Connections → **Network access**, which the docs say restarts the app and should yield **`remote-reachable` with `one-time-token` plus `desktop-bootstrap`**; that exposes beyond loopback and should be paired with Tailscale if needed. Pair once (`t3 pair` or the pairing URL), exchange at `POST /oauth/token`, store the bearer **in the companion service**, never in the browser bundle. Confirm authenticated session and shell, then run the isolated spike. If live `bootstrapMethods` still lacks `one-time-token`, refuse to proceed. Standard pairing scopes include `orchestration:operate`; “read-only companion” is a client choice, not a pairing profile. ([auth.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/packages/contracts/src/auth.ts), [environment-auth.md](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/docs/internals/environment-auth.md))

Completion is reconstructable from the event stream; it is **not** a discrete `turn.completed` orchestration event. Correlate a Rooms run as: the companion’s `thread.turn-start-requested` (`commandId` + `messageId`) is still the pending start when the next `thread.session-set` enters `running` with `activeTurnId`; then **that same `turnId`** leaves `running`. Success is `latestTurn.state === "completed"` for that `turnId`, session `ready` or `idle`, and shell `hasPendingApprovals` / `hasPendingUserInput` false. Failure is `latestTurn.state === "error"` or activity `provider.turn.start.failed` for that `messageId`. Interruption is session `interrupted`/`stopped` settling that `turnId`. **Do not** use `thread.settled` (manual settle and auto-settle share the type; auto-settle can fire later for age or a merged PR). **Do not** key success on “session left `running`” without `turnId`: steering marks the previous running turn `completed` when a new turn starts. `thread.turn-diff-completed` is the **checkpoint** milestone, not provider completion; waiting on it as the success bit stalls when the checkpoint is `missing`. Provider `turn.completed` with state `interrupted` or `cancelled` is stored as session `ready` / turn `completed`. Historical turn state is not on the public snapshot; the companion must keep `commandId` → `messageId` → `turnId` itself. Two-harness sequences remain empirical (PRD spike 3). ([projector.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/apps/server/src/orchestration/projector.ts), [ProviderRuntimeIngestion.ts](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts), [overview.md](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/docs/internals/overview.md), [PRD.md](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md))

T3 has **no native persona or system-prompt field** on `thread.create`, `thread.meta.update`, or `thread.turn.start`. Deliver persona as the first user-message brief and/or repo `AGENTS.md`, which T3 reads itself. Permission mode is first-class via `thread.runtime-mode.set` (`approval-required` | `auto-accept-edits` | `auto` | `full-access`); putting those fields only on `thread.turn.start` does not change what `thread.turn-start-requested` persists. Optional `message.context` is structured composer context, not a system prompt. The UI must not imply a persona string is an enforced permission mode. ([orchestration.ts ThreadCreateCommand](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/packages/contracts/src/orchestration.ts#L1114), [permission-modes.md](https://github.com/pingdotgg/t3code/blob/b954af60c402ff0698f9f2d9a214695e817f07fe/docs/user/permission-modes.md))

## Herdr stays out; Jev and SemIf fail the Phase 2 gate
Rejecting Herdr as the execution backend is consistent with the written gaps, not only with the user’s undiagnosed trial. Live Herdr docs still say `agent.wait` / `agent prompt --wait` **do not track individual turns** and can complete on a pre-existing turn; `unknown` does not prove success. T3 Code is not listed among supported agent kinds. The current Synapse README still describes idle/stable/no-dialog delivery gates, not “release B after task A succeeds.” Those two holes are exactly the section 6 behaviors Phase 1 has to own. Building on Herdr would still mean writing the SQLite graph, cycle checks, revision rules, and outbox; Herdr does not shrink that scope. An idle reviewer would receive a sequential-review assignment early. The trial (could not find harnesses; disliked the product) is a stacked reason, not a substitute for those gaps. Idle, `thread.settled`, and uncorrelated wait are inadequate on **both** backends; the companion must correlate the turn it submitted. A further Herdr pilot is not a prerequisite. ([Agent automation](https://herdr.dev/docs/agent-automation/), [Agents](https://herdr.dev/docs/agents/), [Synapse README](https://raw.githubusercontent.com/vitalysim/herdr-synapse/main/README.md), [HERDR_ASSESSMENT.md](file:///Users/moonmoon/Projects/t3code-rooms/research/HERDR_ASSESSMENT.md), [PRD.md](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md))

Hosted Jev and local SemIf are **optional Phase 2** and are **not** required for any Phase 1 capability. Direct controls, explicit syntax, validation, the durable queue, dependency release, notes, participant attachment, and T3 session operations are specified to work with inference disabled, no Jev key, and no local classifier. TypeSafe docs on 2026-09-23 still match the PRD: `POST /v1/systemone`, Choice/Noul, independent parallel questions, Choice `confidence` from the option distribution, Noul with no confidence field, pin **`jev-1.13.0`**. `TYPESAFE_API_KEY` versus local `JEV_API_KEY` does not matter for HTTP; only `Authorization: Bearer` does. SemIf (formerly OpenJev) is an independent local option scorer without TypeSafe weights, without `POST /v1/systemone`, and without Noul/Score; a room adapter would be custom, and this repository has not installed or scored it. Do not implement either in Phase 1. ## Six graph decisions split “start building” from “Phase 1 complete”
**Can start building now** means an engineer can code the catalog happy path from sections 4.4–4.5, 6.1–6.3, 6.5, and 7: nine operations, three schedule modes, revisioned `after_all`, cycle rejection, frozen briefing, persist-before-send, against a fake adapter, with Jev off. **Can claim Phase 1 complete per section 11** means two implementers persist the same task graph under cancel, edit, retry, and restart; every catalog-plus-native control has a handler; and live harness rows have a defined correlation contract. The first is largely true. The second is not. Stack choice (TypeScript versus Python) does not substitute for these six; two TypeScript implementers still persist different graphs if the rules are undecided. ([PRD.md](file:///Users/moonmoon/Projects/t3code-rooms/PRD.md))

Write these six product decisions as command fields and state transitions **before coding graphs**. They change stored task identity, edges, or dispatch records. None is closed by the catalog table, the mermaid diagram, or a list that only covers stack, auth, and event names.

| Decision | What to write | Dangerous default |
| --- | --- | --- |
| **D1. Identical resend versus `task.retry`** | Two named operations. Outbox **identical resend** reuses the T3 `commandId` and the frozen briefing (T3 will not apply a changed body). User **`task.retry`** mints a new command id and a new run, with a persisted dependent-handling enum: reattach / leave-on-old / block. | One word “retry” that reuses the accepted receipt: no new attempt runs; dependents wait forever. Or minting a new id on crash-unknown-ack duplicates work. |
| **D2. Cancel of a prerequisite** | Cancel of work T3 has not accepted moves dependents **`queued → blocked`** with a visible cancel reason. Draw the edge; section 11 Failures currently lists fail/interrupt/input-block, not cancel. | Dependents remain `queued` “waiting for named tasks” (zombie wait) or cascade `cancelled` so a mistaken extra task looks like a broken predecessor. |
| **D3. Edit of a prerequisite revision** | `task.update` creates revision 2. Dependents of revision 1 **block until the user reattaches** (Add-follow-up’s “exact task/revision” forbids silent retarget). | Leave them on revision 1 (the review never releases) or auto-retarget to 2 (the review of text the user no longer meant). |
| **D4. Mark-blocked** | First-release command from native **`succeeded`** (prose blocker, no native blocked state): treat as failed for dependents still `queued`; **no-op** if dependents are already `dispatching`/`running` (accepted prompts cannot be retracted by editing the card). Phase 2 `report_task_outcome` does not replace this. | Native success releases the review of incomplete work; Sequential review “exactly once” can pass while the product is wrong. |
| **D5. `dispatching` recovery** | Crash matrix: before send, identical resend of the same id and frozen briefing; after send unknown ack, same identical resend; after ack before `running`, identical resend no-ops at T3 — **do not mint a new id**. T3 rejection requires a new identity. Draw edges out of `dispatching` besides `running`. | Mark `failed` and wait for `task.retry`: a second attempt starts while the first turn still starts. |
| **D6. Room revision versus task revision** | Name which token each command checks. Room record has **next event sequence**, not `roomRevision`. Participant has **binding generation**. Task, draft, and interpretation each have their own revision. Binding generation must stale-fail a command that targets a rebound participant. | Mixing “any timeline event stale-fails in-flight commands” with “task commands check only `task.revision`” makes section 11’s stale-revision test have no single oracle. |

A correct adapter that creates threads, submits turns, returns full text, and reports the correlated terminal state still implements whatever release rule the room writes. If that rule is “native success ⇒ release dependents,” a prose blocker ships a review of incomplete work with no T3 bug. If the composer’s “ordinary queue” is implemented as the harness input queue, the review is submitted early, which section 6.3 forbids, and a correct adapter faithfully delivers the early prompt. Steering text, mentions in assistant output, commentary, idle, and `thread.settled` must not create or complete a room task. Context budget is independent of the MCP cap: once full text is available, the room can still drop earlier sibling decisions or hide truncation. Also decide, slightly narrower than D1–D6: one `task.create` with several recipients is **N task rows and N T3 command ids**; predecessor `needs_input` keeps dependents waiting with a visible reason rather than silently remaining `queued` with no Failures row; rebind cannot silently send a pending task to a new session.

Most of section 11 is a **fake-adapter** oracle (contract validation, exact-syntax parsing, fan-in, non-release on scripted failure, restart-before-ack, local context truncation, secrets). Named sessions, live sequential review, real native questions, and spike 3 need **two actual harnesses**. No Phase 1 acceptance row requires a Jev call. The 95%/100-instruction gate is a Phase 2 enablement switch.

## Conclusion
The implementability question splits into two products that the draft PRD currently writes as one. The product that is ready to code is a local SQLite room with explicit Send / Queue / After-both controls and a T3 port that, once paired, already has create, turn, interrupt, approval, full-text read, and command-id receipts — no fork, no classifier, no Herdr. The product that is not ready to claim done is “Phase 1 complete per section 11,” because cancel, edit, retry, mark-blocked, `dispatching` recovery, and concurrency tokens still have two careful implementations each, and because this Desktop Nightly still has no pairing token to give a second process. Shipping the section 1 spoken paragraph, or turning Jev on, would be a third product again: that work is Phase 2, the gate is already failed, and putting it on the critical path is how a buildable queue becomes an unfinishable interpreter.
